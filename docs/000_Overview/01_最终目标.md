# 01 — 最终目标

## 思考（不许跳）

「做股票交易系统」太宽。第一性原理只问：**到了明天开盘，这个系统必须已经产出什么，否则就算失败？**

失败的定义：

- 不知道今天该不该交易（门控）。
- 知道该交易，但不知道买哪几只、各多少。
- 已经持仓，但不知道明天该继续拿、减、还是砍。
- 公式改过，但说不清明天用的是哪一版策略。

所以最终目标拆成两个可检验的产物，而不是「有一个平台」。

## 产物 A — 日频：明天的可执行策略

在 **T 日 15:00 之后**（A 股收盘），系统必须给出 **T+1 开盘** 用的一套指令，且每条指令能指回对象：

1. 账户是否允许新开仓（暂停？熊市空仓？广度不足？）。
2. 已有 Position：继续 / 止损 / 到期 / 减仓 — 每一条对应一个 Position object。
3. 新开：哪些 Stock、建议权重、来自哪张 Signal。
4. 使用的 Strategy 版本号。

「策略」在这里不是一篇研报，而是 **一套待提交或已建议的 Action 列表**。

## 产物 B — 周/月频：策略迭代

每隔一段时间，用 **同一 Ontology 上已经发生的 DailyBar、Signal、Order、Fill、Position** 做样本外评估，决定：

- 改 Function 公式（例如权重），或
- 改 Strategy 参数 struct，或
- 启用新 Strategy、停用旧的。

迭代的输出仍是 Ontology 上的对象变更（新 version、Enable/Disable），不是另存一个 `v47.pkl` 与线上脱节。

## 停：分类

| 念头 | 判定 | 理由 |
|------|------|------|
| 「明天的策略」本身 | **不是** Object type | 它是一组 Action 建议 + 读到的对象状态。若做成 `TomorrowPlan` 类型，会变成时间机器（每天一个新类型或每天一个上帝对象）。 |
| 某一条「明天买入 603016」 | 将来是 **Action** 提交出的 **Order**，提交前是 **Signal** | 能搜到、能批准、能追溯。 |
| 「v46 这套玩法」 | **Strategy** object type | 有版本、有参数、能开关。 |
| 「空仓」 | **不是** 新类型 | 是 `gateOpen=false` 或 Account 无 open Position 的状态。 |

这一步还**没有**引入 K 线。若这里已经去设计 45 个因子，就是思维跳跃。
