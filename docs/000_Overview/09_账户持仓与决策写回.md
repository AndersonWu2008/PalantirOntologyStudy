# 09 — 账户持仓与决策写回

## 思考

「结合历史记录」不只是历史 K 线。Palantir 的 decision capture：过去下没下单、有没有违反行业上限、暂停过没有，都必须是 Ontology 里的对象，否则周月迭代只能对着行情回测、对不着实盘行为。

两条历史：

1. **市场历史** — DailyBar / TradingDay（07、05）。
2. **我们的行为历史** — Signal、Order、Fill、Position、Pause（02 的 Action 写回）。

Fill 是券商事实：Source sync 成交回报 → 源 Property。不要用本地「假设全部成交」覆盖真实 Fill（回测引擎另开 Function，写回 **回测账户** 对象，不要污染实盘 Account）。

## 持仓状态如何更新

- 开仓：`SubmitBuyOrder` → Fill 到来 → Position 开或加。
- 盘中/收盘风控：Function `trailingStopHit` 等 **建议**；真正平仓仍是 Action（人点或自动化 **function-backed action** 由监控触发）。自动化平仓也是 Action，因为改了账本；它与「算 MA」不同。
- `regimeAtEntry`：Position 上的 **快照 Property**，开仓 Action 写入当时 TradingDay.regime。以后制度改写，不影响「入场时的制度」。

## 停：分类

| 事物 | 判定 |
|------|------|
| 资金账户 | Object type Account |
| 持仓 | Object type Position |
| 订单 / 成交 | Order / Fill |
| 现金、股数 | Property（现金随 Fill 变，由 Action/同步写入，属账本事实） |
| 建议止损价 | Function；可快照到 Position |
| 实盘 vs 回测 | 两个 Account 对象，同一套类型（禁止 `BacktestPosition` 第二套类型，那是 System Silos） |

## 需要下载的账本数据

- 券商：成交、委托状态、资金。Sync → 与本地 Action 对账。不一致则报警，不以「策略以为成交了」为准。

## 校验

每笔 Fill 能 link 到 Order；每笔 Order 可选 link 到 Signal；每个 open Position 能走到 Stock 与 Account。断链即账本坏了，禁止开新仓。
