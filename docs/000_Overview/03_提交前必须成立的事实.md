# 03 — 提交前必须成立的事实

## 思考

Action 不能凭空提交。把 `SubmitBuyOrder` 展开成必须已经存在的对象。只问「缺了哪个对象提交条件无法计算」，不问「因子怎么算」（那是 06）。

以「批准后买入 603016.SH 占净值 10%」为例。

## 必须已经存在的对象

1. **Stock** `603016.SH` — 否则买谁？
2. **Account** — 谁的钱？
3. **Strategy** 当前启用版本 — 10% 这个权重从哪来？
4. **Signal** 今日、此策略、此股票 — 否则早盘卡从哪点？
5. **TradingDay** 今天 — 制度、广度、门控输入。
6. **DailyBar** 此股票×今天 — 昨收/今收、是否涨停、ATR（仓位与止损要读）。
7. **Industry** + `inIndustry` — 「每行业最多 2 只」。
8. 已有 **Position** 集合（可空）— 是否已满仓、是否已持同行业。
9. **Index** 成员 link — 是否在 456 池内。

公司、交易所此时也该存在，否则 Stock 的 `listedOn` / `issuedBy` 悬空；它们不参与下单计算，但是 Stock 的身份图的一部分。

## 停：分类

| 事物 | 判定 | 源/派生/决策 |
|------|------|----------------|
| 603016.SH | Object type Stock | 身份是源 |
| 证券简称 | Stock.name Property | 源 |
| ST | Stock.specialTreatment | 源（公告/行情），可用 Action 紧急覆盖并审计 |
| 上交所 | Object type Exchange + link `listedOn` | 源 |
| 申万行业 | Object type Industry + link `inIndustry` | 源（行业映射表） |
| 今天 | Object type TradingDay | 日历是源；regime 是派生（05） |
| 603016 今天的 K 线 | Object type DailyBar + links `hasDailyBar` `barOnDay` | OHLCV 源；指标派生（06） |
| 早盘卡 | Object type Signal + links 到 Stock/Day/Strategy | score 派生快照；status 决策 |
| 10% 仓位数字 | Function `sizePosition`；Order 上可快照 | 派生 |
| 每行业 2 只 | Function 读 links；写入策略参数是 Strategy 源/配置 Property | 规则是 Function+参数，不是 Object |

**不要**把「是否涨停」做成 Object type。它是 DailyBar 上 Function `isLimitUp`。

## 本步需要的数据

仍不必下载。但已经可以列 **对象图缺口**：没有 DailyBar 就无法判断涨停与仓位；没有 TradingDay 就会把制度复制到 456 只股票上（God object）。

## 技能与校验

- Skill：`domain-modeling`（Stock ≠ DailyBar ≠ Signal）、`codebase-design`（Action 入参是对象不是字符串代码）。
- 校验：从 SubmitBuyOrder 画到叶子对象，每条边是 Link 或「读 Property」，没有「从 pickle 里取一行」这种边。
