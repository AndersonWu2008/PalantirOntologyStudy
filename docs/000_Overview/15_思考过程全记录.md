# 15 — 思考过程全记录

本章记录**推演时实际走过的问题**，包括被拒绝的捷径。类型结论以 01–10 为准；这里保留「为什么不跳步」。

## 起点问句

用户要的不是再列一遍 Object type，而是：**从最终目标出发，用第一性原理推到可下载数据**，中间每步分类，并且中间量必须由唯一事实经 Function 得到，不能写死。还要周月迭代。还要把思考过程写全，做成从零到一教程。

因此不能从「我们有 45 个因子所以 DailyBar 要有 45 列」起笔——那是从中间起笔。正确起笔是：「明天开盘若系统宕了，缺的是什么？」

## 链 1：目标 → Action（拒绝「策略是一篇文档」）

若「明天的策略」是 Markdown 建议，Ontology 不必存在。Palantir 的差异是 **Action 改数字孪生**。所以目标必须翻译成「明天可能提交的 Action 列表」。

拒绝：建 `DailyPlan` 上帝对象装下所有建议。那会把持仓、信号、门控塞进一天一个对象（God object），也无法 Search Around「这只股票所有历史计划」。

## 链 2：Action → 必须存在的对象（拒绝先画 ER 图）

从 `SubmitBuyOrder` 反推缺什么：没有 Stock 买空气；没有 Account 不知道谁付钱；没有 Signal 早盘无物可批；没有当日 bar 不知道涨停。这才**第一次有资格**说出 DailyBar。

拒绝：一上来下载全市场 5000 只。广度与 rank 的分母是交易池，不是全市场。先有 Index 规则，再下载池内 K 线（历史全量可以更宽，日频增量以池为准）。

## 链 3：Signal 必须是算出来的（拒绝手填推荐股）

若 Signal 手填，周月迭代无法解释盈亏来自规则还是来自拍脑袋。故 rankUniverse 是 Function，作业物化对象，Approve 才是 Action。

拒绝：Stock.todaysScore。明天分数会覆盖今天，历史决策丢失（Time Machine 的反面：没有历史）。

## 链 4：制度是全市场一天一值（拒绝抄到每只股票）

卡片上的权重随制度变，所以制度是打分输入。但它是聚合量，家在 TradingDay。

拒绝：Regime 做成 Object type（搜「sideways」不如搜日期）。拒绝：每天 Action 选制度（那是把计算冒充决定）。

## 链 5：指标全部是派生（拒绝 pickle 双真相）

用户要求 400+ 只股票的**全部计算指标**都涵盖。涵盖 ≠ 每个因子一个 object。涵盖 = DailyBar 上都能查到，且 `f = Function(源)`。

拒绝：研究 pickle 与线上 Function 各算各的。拒绝：在配置里写死某只股票的 RSI。拒绝：用 Action 每晚写 MA20（Golden Hammer）。

「Function + Action 更新派生」容易理解成「所有派生都靠人点 Action」。那会违反 Palantir。记录下来的分辨：

- 无人值守派生 → Pipeline 执行 Function，写派生 Property。
- 有人的业务提交 → Function-backed Action 把**当时**计算结果写进 Order/Signal（决策快照）。
- 随参数而变、不必落库 → 查询时 derived（gateOpen）。

## 链 6：源数据这才允许「下载」（拒绝一开头 sync）

没有对象图就 sync，只会得到一堆 dataset，然后被迫用系统名建模（System Silos：TencentQuote）。先规定「一行干净 K 线 = 一个 DailyBar」，再连 Source。

多源合并发生在 Pipeline，Ontology 只见统一 DailyBar。

## 链 7：历史记录包含我们自己（拒绝只回测行情）

「结合历史」若只等于 K 线，实盘滑点、拒单、暂停都会在迭代里消失。故 Order/Fill/Position 与 DailyBar 同级重要。回测用第二个 Account，不新建一套类型。

## 链 8：迭代改的是 Strategy 对象不是类型树

拒绝：`Stock_v46`、`SignalTypeV47`。版本是 Property。评估是 Function。采纳是 Enable Action。

## 链 9：施工顺序与理解顺序相反

教程若只给反推，工程师仍会先做 Workshop 空壳。故 12 章强制：Source → 主数据 → K 线 → Function → Signal → Action → Schedule。每层闸门在 14。

## 链 10：技能不是装饰

没有 `domain-modeling` 会出现「板块/行业/Sector」混用。没有 `trading-research` 会把已弃用的龙虎榜评分捡回来。没有 `tdd` 派生列会在「看起来对」中漂移。没有 `grilling` 周月迭代会把样本内最优参数写进生产。这些技能出现在闸门表里，是因为推演中每一处失败模式都对应过一次真实风险（部署脚本 里的前视偏差审查、行业数据断更、未收盘用腾讯实时）。

## 结束条件

当且仅当：

1. 能从「明天提交的 Action」一步不跳走到「哪张 Source 表的哪一列」；
2. 每一跳都有分类记录；
3. 每一个派生列都能指出 Function 与源 Property；
4. 周月迭代不增加市场类型、只增加 Strategy 版本与评估；

这套 Palantir A 股交易 Ontology 才算从零到一**想清楚了**。之后才是 12 章的施工。
